# 通用 VLM 调优策略

本参考描述变量关系和实验顺序，不提供固定最佳值。每个数字都必须由当前项目的模型、量化、硬件、镜像、输入输出和目标重新确定。

## 一、先识别瓶颈层

在改服务参数前，用现有基线判断主要压力来自哪里：

| 现象 | 优先检查 | 不应直接推出 |
|---|---|---|
| 视觉预处理耗时高、NPU 等待 | 输入规模、解码/抽帧/渲染、传输、processor worker、客户端 CPU | 必须增加 NPU |
| 队列高、NPU 利用率高 | 并发、batch tokens、seqs、TP/DP、输出长度 | 增大所有 batch 参数一定更快 |
| HBM 接近上限、尾延迟突然恶化 | KV cache、上下文、显存利用率、碎片、批预算 | 能启动就能稳定压测 |
| 重复输入快、唯一输入逐轮变慢 | 多模态处理器缓存的填充与淘汰 | 缓存越大越好 |
| HTTP 成功但业务输出无效 | 输出上限、校验器、约束解码、调度方式、finish reason | HTTP 200 等于业务成功 |
| 并发提高但 QPS 不升、P95 上升 | 饱和点、负载均衡、每副本在途数、客户端连接 | 卡数不足是唯一原因 |

资源证据缺失时写明缺口，不用猜测替代采样。

## 二、推荐实验顺序

### 1. 固定真实请求

先锁定 work item 定义、输入规模分布、prompt、输出协议、thinking、temperature、工具/流式模式、输出策略、数据复用率、客户端和网络路径。任何一项变化都新建结果序列。

### 2. 校准请求侧成本

- 视觉规模只在业务允许范围内试探，包括分辨率、图片数、页数、视频时长、抽帧数或视觉 token；验收必须回到客户分布。
- 输出上限从真实 completion 分布估算；结构化输出还要给闭合留余量。
- 分别记录截断、格式/协议错误、质量不合格和业务校验失败。
- 先找客户端主并发的大致饱和区，再固定主并发做服务端 A/B。

### 3. 选择拓扑

先确认每个 TP 候选能否容纳权重、视觉编码器、KV 和运行时余量。对短请求吞吐，比较“较小 TP/较大 DP”和“较大 TP/较小 DP”，但所有拓扑必须使用相同总卡数和请求口径。

### 4. 调整并发与批预算

- `max-num-seqs`：小步提高，验证实际在途请求是否接近上限。
- `max-num-batched-tokens`：围绕基线做上下夹逼；至少保留一个较小值、基线和一个较大值。
- 参数扩大后若平均 QPS略升但 P95、最大延迟或重试显著恶化，判为不稳定。

### 5. 调整显存与 KV

- `gpu-memory-utilization` 小步变化，不跨大档位盲试。
- 同时记录启动所需 KV、实际可用 KV、可支持上下文、HBM 峰值和尾延迟。
- OOM、EngineDead 或长尾恶化后先回退，不在故障状态继续叠加参数。

### 6. 单独测试缓存

按业务的数据复用率选择冷、热、重复或唯一输入。多模态 processor cache、prefix cache 和网关响应缓存是不同层，必须分别证明命中来源。缓存 A/B 至少包含一次立即复测，观察填充和淘汰后的漂移。

### 7. 单独测试调度和 CPU

async scheduling、processor worker、OMP 线程和客户端 worker 可能互相影响。每次只改一个，报告 CPU、队列、输出有效率、重试和 P95，不只看吞吐。

### 8. 最后测试上下文

上下文先做容量校验，再做性能验收。若要搜索最大可用窗口：

1. 设定用户要求的上下界和粒度。
2. 对候选做启动与 KV 校验。
3. 启动失败时降低候选；启动成功后仍需跑正式负载。
4. 性能或质量失败也算该窗口不合格。
5. 保留当前最优合格窗口和已验证回退版本。

可以使用二分搜索减少重建次数，但实际候选需对齐模型和框架允许的上下文粒度。

## 三、如何判断结果可比

以下任一项不同，都必须在结果中显式标记：

- 模型、权重 revision、量化或镜像。
- 卡型、卡数、TP/DP、Region 或资源池。
- work item 构成、输入规模分布、预处理、传输方式或数据集。
- prompt、输出协议/校验器、thinking、temperature、工具/流式模式或输出上限。
- 请求数、并发、超时、重试或闭环/开环模型。
- 重复/唯一输入、缓存预热方式或缓存容量。
- 直连/LiteLLM、客户端位置、HTTP 连接复用或网络路径。
- cold warmup、hot warmup、正式运行或立即复测。

不完全可比的结果可用于定位方向，但不能合并计算提升率，也不能替代验收。

## 四、为什么最高成绩可能不采用

常见原因包括：

- 使用了比客户规格更小的输入、更少 work item 或更短输出。
- 请求数太少，只是短诊断。
- 重复输入、共享前缀或响应缓存产生了与生产不一致的复用。
- 只展示成功请求，忽略失败等待和重试。
- cold/hot 状态不同，或网络路径改变。
- 吞吐上升但成功率下降、业务输出无效或尾延迟失控。
- 只出现一次，立即复测无法重复。

最终报告应把这些高值保留在“探索结果”中，并明确不可晋升原因。

## 五、停止搜索

满足以下任一条件时停止当前方向：

- 连续多个相邻候选没有可复测收益。
- 质量、成功率或结构化完整性低于门槛。
- OOM、EngineDead、不可恢复队列或严重尾延迟。
- 达到用户限定的卡数、时间或停机边界。
- 改进小于运行间自然波动，且没有业务安全余量。

此时交付已测范围内的最佳稳定候选、失败记录、证据缺口和下一步；不要声称全局最优。
